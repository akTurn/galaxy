Exactly. This is an important distinction in Galaxy's correlation architecture: detecting a current condition is different from detecting a change over time.

Let's preserve this distinction as we add more rules.

## Current-state vs. historical detection

| Detection type     | Example                                              | Required data                                          |
| ------------------ | ---------------------------------------------------- | ------------------------------------------------------ |
| Current state      | A service is currently `failed`                      | Latest service observation                             |
| State transition   | A running service has stopped                        | Previous and current observations, or lifecycle events |
| Repeated failure   | A service has failed several times within 10 minutes | Timestamped history or lifecycle events                |
| Persistent failure | A service has remained failed for 5 minutes          | Historical observations or a recorded transition time  |

## How this applies to Galaxy

- `FailedServiceRule` detects a service whose current active state is `failed`. It does not establish when the failure began or whether it happened repeatedly.
- `ProcessLifecycleFailureRule` should use lifecycle events or historical observations to identify process exits or repeated restarts, if the collected data supports those conclusions.
- `InactiveCriticalServiceRule` should compare current service states against an explicit list of services configured as critical. An inactive service is not automatically a failure.
- `RepeatedErrorLogRule` needs timestamped log records and reliable error-severity information to count errors over a time window.

One additional safeguard: when a service disappears from the latest observations, Galaxy should not automatically conclude that it stopped unexpectedly. The collector may have failed, or the observation may be missing for another reason.

We'll keep each rule's required evidence explicit and test both positive cases and cases where evidence is missing. That will help Galaxy produce findings that are explainable rather than merely suspicious.

## 3. What I would change before adding more rules

### A. Separate observation, diagnosis and AI

Keep these as separate responsibilities:

- Observation: A service is failed; a process is missing; CPU usage is high.
- Correlation: These observations are related through a service, process, host or application.
- Diagnosis: Evidence suggests the service failed because its dependency is unavailable.
- AI explanation: Explain the evidence and possible causes in understandable language.
- Recommendation: Suggest a safe, specific next step.

This separation prevents an AI model from inventing system facts.

### B. Build an evidence retrieval layer

Before sending anything to a local model, Galaxy should be able to answer questions such as:

- Which services are currently failed?
- Which processes belong to those services?
- What changed immediately before the failure?
- Which recent logs are associated with the affected components?
- Is this condition new, recurring or normal for this machine?

Your SQLite store and graph should provide these answers. You should not need to send the entire database or every log to the model.

### C. Make the monitoring loop reliable

For continuous local monitoring, plan for:

- Collection intervals and timeouts.
- Process and service lifecycle changes.
- Log deduplication and retention.
- Missing or inaccessible data.
- Resource usage of Galaxy itself.
- Tests against actual machine observations.

You already have some of these foundations, including the orchestrator, lifecycle tracking and current-state relationships.

## 4. When should you add a local AI model?

Not immediately. First, make sure the deterministic monitoring and correlation layers work reliably.

Once they do, a local model can provide natural-language reasoning without requiring you to send machine data to an external AI service. A model runner such as Ollama is one possible option.

The local model will still need enough memory and processing capacity, and running locally does not automatically make every operation safe. Keep privileged commands, destructive changes and automated remediation behind explicit controls.

## 5. My recommended next milestone for Galaxy

Rather than adding many more isolated rules, build and validate one complete incident investigation:

1. Galaxy detects a failed service.
2. It checks whether the service's main process exists in the current process snapshot.
3. It retrieves relevant service relationships and recent logs.
4. The correlation engine creates a finding with supporting evidence.
5. The local AI explains the finding using that evidence and identifies uncertainty.
6. Galaxy presents a recommendation without executing a potentially disruptive action automatically.

Your `FailedServiceMissingProcessRule` is a useful small step toward this scenario. Next, test it against the actual store and graph, then expand the investigation to logs and related components.
